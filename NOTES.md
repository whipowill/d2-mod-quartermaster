# Diablo II quartermaster (quartermaster.dll) - engineering notes

Reverse-engineering facts and design decisions, organised by topic (the old chronological stage log was folded into these sections). CLAUDE.md has the summary, standing rules, status and build commands.
The game facts this project depends on (module timestamps, hook signatures, Storm access) are in section 12. Addresses below are D2Game VAs for the stock 1.13d file (image base 0x6fc20000, md5 prefix 3d27210f)
unless noted; **at runtime D2Game is rebased (seen at 0x02980000), so code always works with RVAs** (VA - 0x6fc20000). Items marked **[confirmed]** were verified in the real game; everything else is built from disassembly and only as good as the test noted.
Analysis helper: a few lines of pefile + capstone (`get_memory_mapped_image()`, disassemble at a VA, scan `E8 rel32` for callers); it is not kept in the repo. Do not name a helper `dis.py`.

## 1. Chat and the client side  [confirmed]
- Single-player chat reaches D2Net SendPacket: client->server `15 01 00 <ANSI text> 00 00 00` (size = text + 6; the `arg` of SendPacket is 1 once in a game). The server echoes every line back as `26 01 00 02 00 00 00 00 00 4d <name>\0 <text>\0`,
  so a command must be swallowed in `h_send` (return the last real send result, send nothing) or it appears as chat. Only our own commands are swallowed; other `.xyz` lines pass through (another mod may consume its own commands earlier, at the D2Client chat-send call +0xB2342, found by the pattern `8A 44 24 71 8D 74 24 70 C6 84 24 72 01 00 00 00 E8 ?? ?? ?? ?? E9`).
- Replies: PrintGameString, D2Client +0x75EB0, `void __stdcall(const wchar_t *, int color)`. It must run on the game thread, so messages go through a locked queue (`say`, producers = game thread and server thread) and `h_recv` (game thread, every frame) prints them. Gated on D2Client ts 1318970890.
- Hooks: SendPacket inline detour (chained behind any other mod's hook, see section 10), ReceivePacket IAT hook on D2Client (found by signature, ordinals differ between builds). `g_arg` (SendPacket's 2nd argument) is learned from the game's own gameplay packets (id < 0x60).
- Commands (canonical names; aliases in CLAUDE.md): `.deposit`, `.take`, `.storage`, `.lookup`, `.scan`, and the cheat `.spawn`. Printed instructions always use the canonical names.

## 2. Running code on the SERVER thread without patching code  [confirmed]
- Items belong to the server thread. The server dispatches client packets through a data table: D2Game 0x6fd1a698 (RVA 0xfa698), 8-byte `{handler, flag}` entries indexed by packet id, called as fastcall(ecx = game, edx = player, stack: buf, size), callee pops 8 (dispatcher 6fc873a0 rejects ids >= 0x67 and null handlers;
  caller 6fcf5330 supplies the size). Patching code at the dispatcher call site would collide with any other mod that does the same, so we use the data table instead.
- The byte-stream splitter uses D2Net's client->server SIZE table: VA 0x6fbfabd8 = D2Net RVA 0xabd8, dword per id (id 1.. = 5,9,5,9,5,9,9,5,9,9..., -1 = variable). Unused ids have size 0. Ids with a null server handler: 0x2b 0x4a 0x4e 0x55-57 0x5a-5c 0x64 0x65.
- We take id **0x2b**: size[0x2b] = 9 and slot[0x2b] = {qm_srv, 1}, installed by `patch_thread` (re-checked every 500 ms because D2Game loads when a game starts) only when both entries are still zero, the neighbouring size entries are the stock values and the buy handler (slot 0x32 = RVA 0x6c190) is where it should be.
- The client sends `2b <cmd> <u32 a> <u8 b> <u16 c>` (9 bytes) with `o_send(9, g_arg, p)`; the server thread runs `qm_srv`. Commands: 1 scan, 2 spawn, 3 spawn unique, 4 spawn set, 5 deposit (b = CAT_* mask), 6 withdraw (a = item code, 0 = full rejuv; b = amount).
- Server code reaches D2Common through D2Game's own `jmp [IAT]` thunks (verify `FF 25` before use): RVA 0xa46c first inventory item, 0xa60a next item, 0xa508 item code (dword, space padded) -> item txt index (-1 unknown), 0xa59e item page, 0xa50e set previous page, 0xa5f8 player data (client id at +0x9c),
  0xa5e6 item unit -> item TYPE number (word at record+0x11e; NOT quality, quality is item data +0), 0xa490 item class -> Items txt record (stride 0x1a8, code at +0x80), 0xa6fa save item to buffer. Inventory = player unit + 0x60; unit +0 type (0 player, 4 item), +4 class, +0xc guid, +0x10 mode (item: 0 stored, 1 equipped, 2 belt, 3 ground, 4 cursor, 6 socketed).

## 3. Creating items: the spawn routine and its record  [confirmed for .spawn CODE]
- **D2Game 0x6fd0b050** (RVA 0xeb050), found via the quest code that drops `gld ` piles (e.g. 6fc9d878): eax = code dword, ebx = unit to drop beside, stack (game, 2), ret 8, returns the item unit or 0. It resolves the code (thunk 0xa508), reads the unit's position (6fc2a4a2), finds a free spot (6fd00000), fills a 0x84-byte spawn record
  (mode 3 = ground) and calls the creator 6fd03110 (RVA 0xe3110). The item level comes from the area, so spawned items are levelled to the player's area (an `amu` is a level-appropriate magic amulet: amulets cannot be normal, the game bumps them).
- **Spawn record:** +0x00 owner unit, +0x08 game, +0x0c item level (1 if <= 0), +0x14 item txt index, +0x18 mode (3 ground), +0x1c x, +0x20 y, +0x24 free-spot object, +0x28 word flags (bit0 = add to world), +0x2c "ready-made item" flag (non-zero = restore a saved item using +0x34 quantity,
  +0x38/+0x3c durability, +0x44 item flags, +0x48/+0x4c seed, +0x58..; NOT for generating), **+0x30 requested quality** (stock call passes 2 = normal; 1 low, 2 normal, 3 superior, 4 magic, 5 set, 6 rare, 7 unique, 8 crafted; when non-zero it replaces the rolled quality, 6fd020c3),
  **+0x40 preferred unique/set row + 1** (0 = random). Consumers: creator 6fd03110 -> generator 6fd02040 (quality switch, jump table 6fd02658) -> unique maker 6fd00f10 / set picker 6fc4a9a0 (via 6fc4af60) -> finisher 6fd02690.
- **Forced unique / set (built, untested):** the unique maker loops the runtime UniqueItems table (`root+0xc24`, count `+0xc28`, stride 0x14c, base item at row+0x28); the set picker loops SetItems (`root+0xc18`, count `+0xc1c`, stride 0x1b8, base item at row+0x28, level requirement a signed word at row+0x30);
  `root = **(DWORD**)(g_dg + 0x6fd18260 - 0x6fc20000)`. Each takes row `[record+0x40] - 1` when its flags, base item and level requirement fit.
  We cannot call the creator ourselves (the spawn routine builds the record), so `install_create_hook` puts a `jmp` over the creator's first 6 bytes (`83 EC 20 8B 41 70`, shape 1) or chains onto an existing `E9` (shape 2) to a stub that, only while `g_ovr_on` is set around our own spawn call,
  overwrites record +0x30 (7 unique / 5 set), +0x40 (row + 1) and +0x0c (99). Installed lazily from the server thread, so nothing is executing inside the creator at that moment. It logs the bytes it found and refuses unknown ones.
- **Row index = file row not counting the "Expansion" divider** (the game gives that divider row no id; the same rule holds for ItemTypes and MonStats). Names/codes come from UniqueItems.txt (`index`, `code`) and SetItems.txt (`index`, `item`) through Storm (`list_load`). The first log of `.spawn set 80` showed row #80 = "Tal Rasha's Horadric Crest", so the numbering matches the runtime table.
- `.spawn` is the cheat gated by `[cheats] spawn` (client and server both check).

## 4. Deposit: destroying an item the way a sale does  [confirmed for rejuvs]
- Lesson: a client crashes in a D2Common assertion (null room) when the server announces item state changes in an order it never saw (e.g. a ground item that never left a container). A brand-new item has no old place, so create-then-pickup is safe; check packet order when trying new flows.
- Packet table: 0x32 buy (17 bytes) -> 6fc8c190 -> worker 6fc93a50; 0x33 sell (17 bytes: npc id @1, item id @5, word @9, price @0xd) -> 6fc8b370 -> worker 6fc92a50. The sell worker clones the item into the vendor's inventory (buy-back list), credits gold (6fd009f0), and removes the original with the two calls we copy. Related: 6fd00ae0 (eax = game, esi = item) is a wrapper that tail-jumps the unit-free function 6fc8fc70 (the sell worker uses it to free a surplus clone); 6fcd44b0 places an item in the belt.
- `destroy_item`: `6fc2a50e(item, 6fc2a59e(item))` (previous page = current page), then **6fcfec70** (RVA 0xdec70: eax = item, edi = player, ebx = client id, stack 0x20, ret 4; sends the client the 9d action 5 "remove from container"),
  then **6fcd49c0** (RVA 0xb49c0: eax = player, esi = item, stack (game, 0), ret 8; removes from the owner and frees the unit through 6fc8fc70; the 0 means no second notify). Entry bytes of both are verified first. The callee overwrites its register operands, so the inline asm works on copies.
- Collection rule: items with mode 0 (stored in a container) AND on the inventory or cube page (`INV_PAGE` 0, `CUBE_PAGE` 3, read with thunk 0xa59e; plus `STASH_PAGE` 4 when enabled). The game's internal grid numbers are inventory 0, equipment 1, trade 2, cube 3, stash 4, belt 5 (0xFF none); saved items/packets show them +1 (inventory 1, cube 4, stash 5).
  Stash contents (page `STASH_PAGE` 4) are skipped unless `[storage] stash=1` (default 1; it was 0 at first because the stash was meant to be left alone) AND the stash window is open (2026-11-16: the client reads D2Client UI state `0x11C890 + 0x19*4` (UI_STASH, same table as the chat flag at index 5) and sends it in byte 7 bit 0 of the deposit packet; built, untested - `logging=1` prints `deposit: stash setting N, stash window open N`); skipped items are counted and reported in chat and the log shows their page. Not the belt, cursor, equipment or sockets either. The page numbering comes from the known enum and the +1 save offset; if a deposit finds nothing or takes the wrong items,
  the `deposit: taking ... from page N` / `left alone ... on page N` log lines show the real values. Class match by thunk 0xa508 on the item codes (rvs/rvl, gem and rune codes).

## 5. Withdraw: ground spawn + the game's own pickup request  [confirmed for rejuvs]
- The server creates N items beside the player with the section 3 spawn call and queues each item's guid (`item + 0xc`) on a locked queue (`g_pickq`). The CLIENT thread (`pick_pump`, from h_recv, one per 120 ms) sends the pickup request `16 04 00 00 00 <guid u32> 00 00 00 00` (13 bytes).
  Pickups are not restricted in town.
- Why items land in the inventory: the 0x16 handler (6fc8c5f0 -> 6fc8c1e0, case 4 = item) calls **6fcd68c0** when the packet's last dword is 0 - an auto-store (stacking via 6fcd66e0, free spot via 6fcd34b0, place, notify the client; potions go to the belt through 6fcd5510) - and 6fcd5bd0 (item to the CURSOR) when it is non-zero.
  Our packet sends 0. If there is no room the item stays on the ground and the chat says so.
- Limits: 40 per command (run it again for more), amount 1..255. Both ITEM and AMOUNT are required (the user does not want an "all" form).

## 6. Storage file, item lists, safety order
- `quartermaster.txt` in the game folder (cwd), shared by every character: `rejuv_halves=N` and one `<code>=<count>` line per gem/rune. Rejuvenation counts in halves: rvs = 1, rvl = 2; a withdrawal hands out only full rvl (2 halves each) and an odd half stays banked.
  Written through a temp file + `MoveFileEx(REPLACE_EXISTING | WRITE_THROUGH)`.
- **Safety order = never LOSE an item:** deposit writes the file BEFORE destroying (and rewrites it if some destroys failed); withdraw writes AFTER creating. A crash in between can duplicate a few items (single player, accepted), never lose them.
- Gem and rune lists come from the game's Misc.txt via Storm (`parse_misc_cb`): runes = type `rune` (name stored without " Rune"); gems = types gema/gemd/geme/gemr/gems/gemt/gemz (7 families x 5 grades; jewels excluded because they carry properties).
  The client loads them before sending a command; the server only reads them.
- **Essences** (`[storage] essences`, CAT_ESS = 8): Misc.txt rows of type `ques` whose name contains "Essen" (the table spells one "Essense"): Twisted Essence of Suffering `tes`, Charged Essense of Hatred `ceh`, Burning Essence of Terror `bet`, Festering Essence of Destruction `fed`. Same deposit/withdraw/spawn path as gems and runes;
  Displays use the first word of the game's name (Burning, Festering, Twisted, Charged: `ess_short`). `.withdraw` accepts the code, the full name, the short word ("burning"), "essence of terror" or just "terror". They are quest-type items (untested: whether the spawn routine and the pickup handle them like ordinary items). `misc_find_code` now returns a KIND_ (gem/rune/essence), not a rune flag.
- **Keys** (`[storage] keys`, CAT_KEYS = 16, KIND_KEY): the three Misc.txt `ques` rows named "Pandemonium Key 1/2/3" (`pk1`-`pk3`, shown as Terror / Hate / Destruction by `key_short`). Same deposit/withdraw/spawn path as essences; `.take` accepts the code, `key 1`, `terror`, `key of terror`. Built 2026-11-16, untested in game (like essences they are quest-type items). **Organs** (`[storage] organs`, default 0, CAT_ORGANS = 32, KIND_ORGAN): Misc.txt `ques` rows with codes dhn/bey/mbr (Diablo's Horn, Baal's Eye, Mephisto's Brain), shown as Horn / Eye / Brain (`organ_short`); `.take` accepts the code, the full name or the short word. Same path as keys; built 2026-11-16, untested.
- **Shards** (`[storage] shards`, default 1, CAT_SHARDS = 64, KIND_SHARD): Worldstone Shard, code `wss` (matched by code, any item type). The item does NOT exist in stock LoD. In the user's game it used to be the Rancid Gas Potion (`gps`) row of Weapons.txt re-typed as a misc item (graphic `invwss`), and the other five throwing potions were re-typed the same way and dropped from `Misc 0-2`. 2026-11-16 (at the user's request) those six rows and `Misc 0-2` were restored to stock, `wss` became its own row at the end of Misc.txt (type `misc`, level 24, cost 24000, `flpgsr`/`invwss`, not spawnable), `TreasureClassEx` `Orbs` now drops `wss`, the `world shard` cube recipes use `wss` as input 2 and the `TOA -> W Shard TESTING` recipe outputs `wss`, and the name string `wss` = "Worldstone Shard" is in `Data/local/lng/eng/patchstring.tbl`. Backups next to the files: `*.before-wssfix.txt`, `Misc.before-wss.txt`, `patchstring.before-wss.tbl`. `.storage shards`, `.take shard 1`, `.deposit shards`.
- Reports and receipts never print zero counts (`add_part`): the deposit receipt, the `.storage` totals and the per-type reports list only what is non-zero; an empty store says "Storage: empty".
- `.storage` is client-side (`cmd_storage`, reads the file): no argument = totals for the enabled types; `gems` = one line per family (Misc.txt type, grouped in table order), grades highest first (label = the name minus the family base name, ranked chipped < flawed < normal < flawless < perfect,
  family name pluralised from the base name, e.g. Ruby -> Rubies); `runes` = highest rune first, wrapped. Chat lines are cut at ~95 characters including the prefix, so reports wrap at 74 (`LINEMAX`) and `say` always terminates the buffer. `[storage] rejuv|gems|runes` switches each type (client and server check).

- **Town-only option (`[storage] town_only`, default 1):** `town_ok(player)` runs at the start of the server-side deposit and withdraw (so it also covers the Insert key). The level number is read from the server unit: `unit+0x2c` (path) -> `+0x1c` room -> `+0x10` room data -> `+0x58` level -> `+0x1d0` level number
  (+0x1d0 is confirmed by D2Common's own level builder; the rest is the standard 1.13 layout). Town levels 1, 40, 75, 103, 109. An unreadable chain refuses (fails closed). Every check logs `town check: level N -> ...`; if the option ever refuses in a town, that line shows the value that was read.
  `.storage` and `.lookup` are read-only and always work.

## 7. The deposit key
- `[keys] deposit` (default Insert; a key name, F1-F12, a letter/digit, a VK number or `none`; `parse_key`). `key_thread` polls GetAsyncKeyState every 40 ms with an edge detector and fires only when the window is focused, the player exists (D2Client +0x613C0 = GetPlayer) and the chat box is closed
  (UI var 5 = a DWORD at D2Client +0x11C890 + 5*4). It only sets `g_key_req`; `h_recv` (game thread) runs the deposit. Never call game code from the key thread.

## 8. Item serialization and cloning (understood, not used yet)
- The game clones an item by serializing it to bytes and loading them back. Clone routine **6fd02c40** (Items.cpp; eax = game, stack (item, 1 = also clone socketed children); ret 8): `6fc2a6fa(item, buf, 0x400, 1, 1, 0)` writes the item's save-format bytes and returns the size; `6fc2a7de(buf, size, 1, &P)` parses a header into a location struct;
  loader **6fd02b70** (edi = game, esi = &P, stack: class, buf, size, 1, &status, 0x60; ret 0x18; creates the unit via 6fc8fe10) makes a NEW floating item; flags are set with `6fc2a766(item, flag, on)` (0x80000, 0x2000, 0x8000000); the vendor case inserts it with 6fcd71a0.
- Consequence: the storage file could hold the real serialized bytes of ANY item (hex) and restore it exactly - the route to storing non-fungible items later. `.scan` logs every owned item's class, mode, guid and serialized hex to quartermaster.log (the format is not yet captured).
- Assertion strings name the source files, which identifies functions: `ITEMS\Items.cpp` (0x6fd1af0c), `ITEMS\ItemMode.cpp` (0x6fd1b3ec; drop 6fcd7fc0, place-by-body-location 6fcd80f0, equip place 6fcd6350, cursor-to-container 6fcd7640, gold 6fcd49c0 is NOT gold: it is the destroy routine of section 4),
  `INVENTORY\InvMode.cpp`, `PLAYER\PlrTrade.cpp`, `UNIT\SUNITNPC.CPP`, `PLAYER\PlrSave.cpp`. Debug string `ITEMSReadInfoFromStreamVersioned` at 0x6fd1e8e8.

## 9. Other server facts found on the way
- Packet 0x4f = click button (7 bytes: word button @1, word @3, word @5), handler 6fc8cf60 -> dispatcher 6fcb8210. Buttons 0x12-0x14 need interaction state 2 (stash gold), 0x17-0x18 need state 4 (cube open): 0x17 closes the cube, 0x18 = Transmute -> 6fcb7cb0 (walks the recipe table).
  The cube's recipe executor was not traced (not needed: the spawn routine and the loader cover creation).
- The game uses unit tables on `game`: monsters at +0x1320 (128 chains, next at +0xe4), items at +0x1720 (same layout), guid at +0xc.

## 10. Coexistence with other mods that hook SendPacket (important)
Another DLL may already have inline-hooked D2Net SendPacket, and some such hooks only accept the stock first byte `A1` (`mov eax,[abs]`), so they fail if we hook first. We therefore detect the stock shape (`A1`) or an existing `E9 jmp` (bytes 5..13 are the stock tail either way) and, when
a mod of that kind is loaded, wait up to 30 s for its `E9` to appear and chain onto it (our trampoline re-creates its jmp). If nothing else is loaded we hook the stock bytes. The receive hook is an IAT hook on D2Client and chains naturally. The server-thread entry (section 2) is a data-table slot,
so it cannot conflict with another mod's code patches. If another mod must load AFTER us, its inline hook needs the same `E9` tolerance.

## 12. Game facts this project depends on (stock LoD 1.13d)
- Module timestamps: D2Game 1318970639 (0x4E9DE50F), D2Client 1318970890; every patch is gated on them. Preferred bases D2Game 0x6fc20000, D2Client 0x6fab0000, D2Net 0x6fbf0000 (D2Game was seen relocated to 0x02980000, so always use RVAs).
- D2Net export ordinals differ between builds, so the two hooked functions are found by code: SendPacket (stdcall ret 0xC) = `A1 <abs32> 85 C0 75 05 33 C0 C2 0C 00` (with the first 5 bytes possibly replaced by `E9`); ReceivePacket (stdcall ret 8, polled every frame - never log empty polls) =
  `8B 44 24 04 50 8B 44 24 0C 68 <q> 68 <q+4> E8 ?? ?? ?? ?? C2 08` with q+4 equal to the second pushed constant. Send and receive each match exactly one export in D2Net.
- Reading the game's own data tables: Storm.dll ordinals 268 SFileOpenFileEx, 265 SFileGetFileSize, 269 SFileReadFile, 253 SFileCloseFile, each verified by first bytes (`8B 4C 24 10 81 EC 10 01`, `56 57 8B 7C 24 10`, `8B 44 24 14 8B 4C 24 10`, `57`). #268 takes a search scope: 3 (loose Data folder first, then the archives)
  when the command line contains `-direct`, else 0. Tables used: `Data\global\excel\UniqueItems.txt`, `SetItems.txt`, `Misc.txt`. Call from the game thread.
- Never use IsBadReadPtr in hooks (it trips stack guard pages); use a VirtualQuery-based check.
- Item and unit conventions are listed in section 2; the packet-level pickup format is in section 5.

## 13. Holy Grail tracker (built, untested in game)
- File `quartermaster_grail.txt`, lines `kind|index|name|found on|found by` (kind unique/set; the last two empty = not found). The lists come from the game's own UniqueItems.txt, SetItems.txt through Storm (names are the string-table values, the same as `.lookup`), so a mod's changes are followed; rows with `enabled=0` are not counted. Keyed by runtime index (section 3 rule). Runewords are not tracked (their id could not be located in the item data).
- Detection runs on the server thread: the client sends command 7 (`gr_pump`) at most once a second, only after `h_recv` saw an item packet (0x9d = owned item action, or 0x9c with action not 0/2/3 = ground add/drop/on-ground; packet ids and actions from the D2GS protocol, not yet confirmed in this game - `logging=1` shows the ids); a scroll-of-identify is not known to produce one, so `.grail scan` is the manual catch-up; `srv_grail` walks the whole inventory (stored, equipped, belt, cursor, stash) and queues each IDENTIFIED item once (`g_gr_rep`); the client thread drains the queue (`gr_apply`: file, date, character name, chat). The first scan credits everything the character already owns.
- Item data = unit +0x14, offsets confirmed by disassembling stock D2Common: +0x00 quality (5 set, 7 unique), +0x18 flags (0x10 identified; the known ethereal 0x400000 fits the scheme), +0x28 unique/set table index (D2Common ord 10075 getter / 10360 setter), +0x45 page, +0x30 format.
  The index is accepted only if the runtime table row's base item (row+0x28 = the 4-char item CODE dword, as in the unique maker 6fd00f10: `cmp [row+0x28], [itemrecord+0x80]`) equals the item's code (thunk 0xa490: item class -> Items txt record, stride 0x1a8, code dword at +0x80); mismatches are logged (`grail: ... ignored`). An earlier version compared the row with the class number and rejected everything.
- `.grail scan` (`scan_saves`) reads `Save\*.d2s`, `*.d2x` (PlugY personal stash pages) and `*.sss` (PlugY shared stash; any name, so hardcore ones are included; label `Shared Stash` / `Shared Stash HC` by file name). Every item record starts with `JM` + 32 flag bits; only the head is parsed (flags 0x10 identified / 0x10000 ear / 0x200000 simple / 0x800000 always set, version 10 bits >= 100, 18 location bits, code 4x8, sockets 3, id 32, ilvl 7, quality 4, picture flag 1 (+3), class flag 1 (+11), index 12). Tested with a Python version on every save in the QOL game folder: 944 items in the shared stash, 287 unique/set, all indexes matched the base item of their table row. Date = file modified time, character = name in the d2s header / file name. Existing entries are never overwritten; it then asks the server to re-report the live inventory (command 7 with b = 1 clears `g_gr_rep`). The match requires row base item == item code; a few rows like Titan's Revenge have more than one base code, so a rare find on another base is skipped.
- Messages: a new find prints one line, "Congratulations! You are X% complete on your Holy Grail quest." (the item names are not printed; they are in the log and the grail file). `.grail scan` prints only a summary ("Added N new item(s) to your Holy Grail." or "No new items..." + the percentage line): live finds that arrive within 1.5 s of the scan are added quietly (`g_scan_pending`).
- `.grail missing [unique|set] [N]` lists the first N (default 5, max 15) items not found yet.
- Character name = player data (thunk 0xa5f8) +0, printable ASCII, else "unknown".
- Thunk 0xa5e6 returns the item type number, not quality; the `spawn unique|set` log now reads quality from item data +0.

## 14. Replies go to the player who asked (2026-11-13, built, NOT tested in a game)
- Before: every reply a server-thread handler made (`.deposit`, `.take`, `.spawn`, `.grail` result lines, `.scan`) went through `say()`, which queues for the local client's `h_recv` -> PrintGameString. In a TCP/IP game the server runs in the HOST's process, so those lines appeared on the host's screen whoever had typed the command; a player who joined saw nothing (and a bot host printed every bot's replies).
- Now: `qm_srv` sets `g_srv_tid` (the server thread) and `g_reply_player` (the sender) while it runs a command; `say()` on that thread calls `srv_reply`, which sends the line to THAT player's client with the game's own routine D2Game 6fcfd190 (RVA 0xdd190: eax = chat record, stack = client; it builds the 0x26 packet and sends it through 6fcfb780; the chat handler 6fc89300 uses it for each recipient). The line arrives as a chat line from "Quartermaster" (record: [0] 0x26, [1] 1, [3] 2, [9] 0x4d, name at +0xa, text at +0x1a, under 256 bytes or the game exits). The prologue bytes are checked before the call; the colours are the same inline codes (U+00FF 'c' N, sent as byte 0xFF). Client = `playerdata(+0x9c)`.
- Unchanged: replies computed on the CLIENT (`.storage`, `.lookup`, `.grail` totals, the swallow of the typed line) are still queued and printed by the local client. The automatic grail message ("Congratulations ...") is produced by the host's game thread (`gr_pump`) after the server found the item, so it still appears on the host's screen, whoever found it. The grail file itself is written correctly for every player.
- Not verified: how the client shows a 0x26 type-1 line from a name that is not in the game, and whether the D2BS chat event of a bot copes (the Qolbot handlers only look at the leader's name or fixed phrases, so they should ignore it). This replaces printing through PrintGameString for those replies, which is the call the user feared could crash bots.

## 20. Stash organizer (design, 2026-11-16 - NOT built yet; the rules file draft is `src/quartermaster_organize.cfg`)
Goal: sort the PlugY shared stash (and personal pages) by the user's page scheme (their `Stash.md` guide). The user's decisions, in order of importance:
- **Triggers.** (1) `[organize] auto=1`: every time a character loads, the in-box pages (default 1-9) are emptied into their pages. (2) `.organize`: sorts the page being looked at: on a shared page its items go to their rule pages; on a PERSONAL page it takes every item on that page and tries to move
  it into the SHARED stash (to its rule page) - whatever cannot be placed stays on the personal page. Bound to a key (`[keys] organize`, default **Delete**); only works while the stash window is open (same UI-state check as `stash=1`, D2Client UI var 0x19).
  (3) `.organize scan`: the entire shared stash; it does NOT need a stash window open (unlike `.organize` and its key). No preview/dry-run feature (removed on purpose). Chat output is only for a typed command and is one short line (`org_summary`): "The shared stash has been organized. X items could not be placed and are found on pages Y-Z." The automatic sort on load is silent (the detailed messages go to the log).
  Items that cannot be placed stay where they are (in-box leftovers are packed toward the first in-box page); nothing is ever deleted or duplicated.
- **Rules file** (`quartermaster_organize.cfg`): `[organize]` settings, type `[group]`s, `[rule]`s (`quality`, `type`, `pages`, `mode = sorted|backload`, `order`), `[sets]` (one page per set).
  The most specific type wins when an item fits several rules (a throwing axe -> knives, not axes). `untouched = 10-29` marks hand-managed pages the sorter never reads or writes.
  `mode = backload` (charms, jewels, rings, amulets, quivers, bases): new items go to the LAST page of the block with room, nothing already there moves; the user pulls the good ones forward by hand.
  Runeword blocks (400-499) hold finished runewords from the first page forward and bases (normal/superior, sockets or not) backloaded from the last page.
  `packing = tight`: use every square (stash pages are 10x10 when PlugY `ActiveBigStash=1`, else the game's Inventory.txt grid); `lookahead` pulls later items forward to fill holes.
  Duplicates: `duplicates = best`, only unique and set items, unsocketed only (any socket exempts an item and it does not count toward `max_copies`), rings/amulets exempt; the worse copies stay where they are for review.
- **PlugY facts (source v14.03 in `plugy_src`, matches the user's PlugY.dll md5 bbec249e...):** each loaded character gets its own copy of the shared stash (`PCPY->sharedStash`), built from the `.sss`
  by `loadSharedSaveFile(ptChar, data, size)` (in PlugY.dll at VA 0x10023500, base 0x10000000: eax = ptChar, ebx = data, size on the stack, caller pops it; prologue `51 56 8B F0 85 F6`).
  Callers: 0x10013318 (client side, data received from the server) and 0x10012c66 (single-player/server load, reads the file with readSharedSaveFile near 0x100233ae). PlugY never reloads or frees
  the shared stash during a game. `handleServerUpdate` (packet 0x3A custom message, PlugY.dll around 0x100264a5) has: select personal/shared stash, US_SAVE (= `/save`), swap page N.
  Grid: `ActiveBigStash` in PlugY.ini (default 0 in PlugYDefault.ini) forces 10x10 on Inventory records 12 and 28; no other size option exists.
  Planned hook (sort on load): detour loadSharedSaveFile, sort the bytes, call the original with the sorted copy, free ours; pass the original bytes through on any failure.
  CORRECTION (source and PlugY.dll read 2026-11-16): loadSharedSaveFile runs on the SERVER only - from LoadSPPlayerCustomData (single player, reads the file; call at PlugY.dll 0x10012c66) and from LoadMPCustomData (a TCP/IP host loading what a joining client sent;
  call at 0x10013318, only when PlugY.ini ActiveSharedStashInMultiPlayer is non-zero). The client never loads the whole file: it gets stash pages from the server when it selects them. So the sort needs no client twin.
  Guard (user's decision: outright, whatever PlugY.ini says): the organizer is for SINGLE PLAYER only. The hook reads its return address: only the single-player caller (LoadSPPlayerCustomData, 0x10012c66 in the user's PlugY.dll) may organize; the multiplayer caller
  (found from the "Start LoadMPCustomData" log string, `g_org_mp_ret`) and an unidentifiable caller are left alone, for the automatic sort and for typed requests (a pending request is cancelled with a chat line, never kept). `g_org_mode` (1 = single player, 2 = multiplayer,
  0 = unknown) is set by each load and reset when the player leaves a game (`org_game_watch`); a typed command is refused at once with "The stash organizer is disabled in multiplayer games." unless mode is 1. A game this process never loads a stash for (joining a host,
  Battle.net) leaves the mode at 0, so it is refused too.
- **File format (verified on the user's stash 2026-11-16, `tools/sss_prototype.py`):** `SSS\0` + "02" + gold u32 + page count u32; per page `ST` + flags u32 + name\0 + `JM` + u16 top-level item count,
  then one record per item: `JM` + bit-packed item (flags 32, version 10 bits, mode 3, bodyloc 4, column 4, row 4, page 3, code 4x8 ...); socketed gems/runes follow their parent (mode 6) and are NOT counted.
  Splitting records at `JM` + a plausible head (version 99-106, mode <= 6) reproduces every page count exactly (490 pages, 1028 items, 85 socket children, 0 mismatches).
- **Command prefix:** every quartermaster command works with `.` or `/` (`.organize` / `/organize`, `/deposit`, `/take`...); `parse_command` already accepts both for the existing commands and `organize` must go in the same list.
- **Personal -> shared moves** touch two lists (the character's own stash pages and the shared pages), so the personal `.d2x` data and PlugY's `PCPY->selfStash` are involved as well as `sharedStash`.
- **Built 2026-11-16 (first test milestone: sort on load), untested in the game:** `src/organize.c` + `organize.h` (pure core: tables, rules file, record splitter/head parser, classification with most-specific-type, packer with
  tight/strict + lookahead, sorted and backload modes, set pages, untouched pages, internal re-parse check) and the hook in quartermaster.c (`org_install` finds PlugY's loadSharedSaveFile by its first bytes `51 56 8B F0 85 F6 0F 84 .. .. .. ..
  85 DB 0F 84` plus the `81 3B 53 53 53 00` check, detours it with `qm_org_stub` -> `qm_org_hook`; chat lines are held in `g_org_pending` until the player exists). Installed only when quartermaster.ini `[organize] enabled=1` and `auto=1` (the rules file is not meant to be edited, so the switches live in the ini; `enabled` defaults to 1, `auto` to 0) at game start; with `enabled=1` and no PlugY.dll loaded the user gets a chat alert and a log line (the organizer is switched off);
  the cfg is re-read at every character load, the game tables (loose `Data\global\excel\*.txt` only) once. Verified natively on a copy of the real stash (`./test.sh`, see its header): 1028 items in = out, every record
  identical except col/row, no overlaps, second pass moves nothing. Prefix/suffix ids are 1-based (row = id - 1).
- **Page layout (user, 2026-11-16):** `untouched = 1-9` (hand pages), `inbox = 10-19`, `rejects = 20-29`. Two kinds of "rejects": a duplicate over the limit goes to the reject pages (front first, not backloaded; not built yet);
  an in-box item that could not be placed (no rule, or its block is full) stays in the in-box and is pulled forward into free squares of earlier in-box pages (implemented: only later-page items move to earlier pages, so a second run changes nothing).
- **Behaviour fixes after the user's first test (2026-11-16):** a sorted block is now laid out again on every run (not only when something arrives); backloaded blocks and set pages are processed before the sorted blocks; `org_sort` repeats the sort on its own result until a pass moves nothing (so a second run never changes anything); ties between identical items are broken by their saved bytes, not their position.
- **Built later the same day (untested in the game):** the property reader in organize.c (stat lists, validated: all 1028 extended items of the user's stash end exactly at their record end); `duplicates = best` (unique/set only, unsocketed,
  `duplicates_skip` types exempt; copies are ranked by where their rolls sit between the lowest and highest values among the copies held; the worst over `max_copies` go to the outbox pages (front first), outbox pages are never swept back);
  `.organize` / `/organize` (the shared page you look at, only with the stash window open) and `.organize scan`; the `[keys] organize=Delete` key (needs `[organize] enabled=1`). **Live (built 2026-11-16, untested in the game):**
  findings from the user's `.stashdump` (a read-only diagnostic) and trace logs: at join the client receives one item packet per stash item (about 1074 0x9c), a page flip sends only two 0x9D custom messages (select stash, page name), and the client's per-page
  lists hold the same unit ids as the server's (chained in the opposite order). So the live run needs no packets: `do_organize` flips to a personal page with PlugY's own message (3A 1B 00 = US_SELECT_SELF; every shared item is then in a list on both sides),
  `srv_live` (server thread, packet 0x2b command 9) calls `lv_run` (organize_live.c): read both sides' lists, build the stash image from the server's units (the game's own item-to-bytes, D2Game+0xa6fa), sort it with the same organizer (page limit = the pages that exist),
  check everything (same ids and pages on both sides, saved places equal the units' paths, every item matched exactly once), and only then rewrite the lists and `path->x/y` on BOTH sides by unit id. Then `live_pump` flips back to the shared page the player was on
  (SELECT_SHARED 0x1C, then NEXT_INDEX2 0x22 / NEXT_INDEX 0x1E / NEXT 0x1A as the page flags allow). WARNING: do NOT use PlugY's US_SWAP3/2/1/0(_TOGGLE) messages (the /swappage and /togglepage commands): they EXCHANGE the items of two pages (found 2026-11-17: it swapped personal page 1 with shared page 10).. The file PlugY writes on save comes from the SERVER's lists (SaveSPPlayerCustomData), so the sorted state is what is saved.
  organize_live.c is pure C over an abstract memory interface; `test/live_test.c` builds PlugY-style structures from a copy of a real stash and checks both sides against the organizer's own result (all 3 scopes pass, second run moves nothing).
- **Outbox scope (user, 2026-11-16):** a single-page `.organize` may only push items to the outbox that sit in a block it sends an item to (or that it is itself picking up); other surplus copies wait for `.organize scan` / the sort on load. Duplicates are judged over the whole stash in those two.
- **Personal pages as a source (built 2026-11-16, untested in the game):** `.organize` / Delete on a PERSONAL page takes every item of that page into the shared stash. The page's items are in the inventory while it is open, so `do_organize` first opens a
  neighbouring personal page (PREVIOUS 0x19, or NEXT 0x1A from page 1 - PlugY adds an empty page if there is none; the way back uses the opposite message); `lv_run(import_page)` then reads that page's list on both sides, `org_stage` puts the items on a hidden staging page in their own places;
  hidden staging page of the stash image, and an ordinary single-page run on it sends each item to its block (the inbox is not used), and the new shared lists plus the personal list (only the items that found no room are left on it) are written on both sides.
  Items that cannot be placed stay on the personal page; chat adds "N items sent from personal page P to the shared stash." and "N items stayed on this page." Mock tests: `LIVE_IMPORT=90 .out/live_test ...` (all items conserved, both sides identical, runs settle).
- **No page flipping (built 2026-11-17, untested in the game):** `.organize` / Delete on the page you are looking at (shared OR personal) parks that page's items on shared page 999 (`PARK_PAGE`) with PlugY's swap (US_SWAP3 0x2F, SWAP2 0x30, SWAP1 0x31, then SWAP0 0x32 for a shared page or SWAP0_TOGGLE 0x33 for a personal page; the argument bytes are the 0-based page number). PlugY creates the missing pages on both sides and leaves trailing empty pages out of the save, so 999 costs nothing once it is empty again. The mod waits for the 0x9D/0x18 reply, runs `lv_run(page scope 999, open_shared = P)` (a shared P is blocked: never a target, items destined for it stay on 999), then swaps back so what is left returns to the page you are on. Page 999 must be empty ("Page 999 ... is in use" otherwise). `.organize scan` still flips to a personal page. `/swappage` and `/togglepage` EXCHANGE the items of two pages (same stash / other stash); they do not navigate.
- **Outbox sale (built 2026-11-17, untested in the game):** `.organize sell` / `[organize] autosell`. `sell_start` -> per non-empty outbox page O: swap(P,O) (US_SWAP 0x2F-0x32, or 0x33 from a personal page), wait for the 0x9D/0x18 reply, server command 9 with scope 5 -> `srv_sell`, swap back. `srv_sell` collects the inventory items on the stash grid (page 4), prices each with D2Common #10186 via D2Game's thunk 0xb0de: `(player, item, difficulty = byte game+0x6d, quest data = *(playerdata + 0x10 + difficulty*4), vendor class id, 1 = sell)` (found by reading the sell worker at 0x6fc92a50: the wrapper's `ret 0x18` = six arguments, the fourth comes from D2Game 0x6fc211d0), reads the gold stat with #10550 (thunk 0xa3b8, stat 14), the maximum with #11159 (thunk 0xa74e), removes the item with `destroy_item`, then adds the gold with #10645 (thunk 0xa3a6, (unit, 14, amount, 0)). The D2Common #10186 entry bytes and all thunks are verified first. The overflow handling of the game's own gold function 0x6fd009f0 is NOT used: a sale stops instead when the gold limit would be passed.
